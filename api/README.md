# api/

FastAPI service wiring `ingestion`, `forecast`, and `settlement-engine`
together -- the first piece of Glasshouse you can actually point a
browser (or `curl`) at and get a live, computed price back.

## Routes

| Route | What it does |
|---|---|
| `GET /health` | liveness check |
| `GET /prices/latest?limit=48` | most recent stored system prices, from `ingestion`'s SQLite store |
| `GET /forecast/system-prices?date=` | seasonal-baseline price forecast for a date (`forecast/`) |
| `GET /forecast/fuel-generation?date=&fuel_type=` | same, for one fuel type's generation |
| `POST /settle` | the raw settlement engine, direct passthrough -- give it any generator/consumer portfolio, get an itemised bill back |
| `GET /quote?date=&business_type=&renewable_share=` | **the one-click endpoint**: builds a synthetic portfolio for a business type, settles it, and benchmarks it against a real forecasted system price |

Interactive docs (Swagger UI) are auto-generated by FastAPI at `/docs`
once the server's running -- genuinely useful for poking at this by
hand before wiring up a frontend.

## Usage

```bash
cd api
uv venv && uv pip install -e ".[dev]"
uv run pytest -v                     # 16 tests

uv run uvicorn glasshouse_api.main:app --reload
# -> http://127.0.0.1:8000/docs
```

`uv pip install -e .` resolves `glasshouse-ingestion`, `glasshouse-forecast`,
and `glasshouse-settlement` as local, editable path dependencies (see
`[tool.uv.sources]` in `pyproject.toml`) -- including compiling the
Rust extension automatically, the same as it does inside
`settlement-engine/` itself. One `uv pip install`, no separate
`maturin develop` step needed here.

By default the API looks for `../ingestion/glasshouse.db`. Override
with the `GLASSHOUSE_INGESTION_DB` environment variable if yours lives
somewhere else:

```bash
GLASSHOUSE_INGESTION_DB=/path/to/glasshouse.db uv run uvicorn glasshouse_api.main:app --reload
```

## Try it

```bash
curl -X POST http://127.0.0.1:8000/settle -H "Content-Type: application/json" -d '{
  "generators": [
    {"id": "wind_farm_1", "available_mwh": 5.0, "cost_gbp_per_mwh": 30.0},
    {"id": "gas_peaker", "available_mwh": 100.0, "cost_gbp_per_mwh": 80.0}
  ],
  "consumers": [
    {"id": "bakery", "demand_mwh": 2.0},
    {"id": "brewery", "demand_mwh": 8.0}
  ]
}'

curl "http://127.0.0.1:8000/quote?date=2026-08-05&business_type=factory&renewable_share=0.6"
```

## Why `/settle` and `/quote` call the Rust engine directly, not over HTTP

`glasshouse_settlement` is imported and called in-process, the same
way any other Python dependency would be -- there's no second service
to run, no network hop, no serialization boundary between the API and
the pricing math. See `docs/adr/0001-python-rust-boundary.md` for the
reasoning; this is that decision actually paying off, not a new one.

## Why `forecast` isn't a hard dependency for `/quote`

`/settle` and `/quote`'s settlement result don't need any historical
data at all -- they price whatever portfolio you send them. The
`/forecast/*` endpoints return `404` when there's no history yet
(`InsufficientHistoryError`), because a forecast with literally nothing
behind it isn't a real answer. `/quote` treats a missing forecast
differently: the benchmark fields just come back `null` rather than
failing the whole request, because the settlement result is still
useful on its own even with nothing to compare it to. Both choices are
deliberate, not inconsistent -- see `test_quote.py`'s
`test_quote_still_works_with_no_ingestion_history_at_all`.

## The `/quote` portfolio is illustrative, not measured

There's no real per-business consumption data feeding this project.
`quote.py`'s `BUSINESS_DEMAND_MWH` and the wind/gas cost assumptions are
stylised, roughly plausible figures for a single settlement period --
useful for demonstrating the pricing mechanism, not a real quote for a
real business. The `/forecast/*` and `/prices/latest` endpoints, by
contrast, are real GB market data end to end.

## A second implementation exists too

`frontend/` is a **parallel** Django + DRF implementation of this same
pricing surface, not a client of this API -- see `frontend/README.md`
for why. Both exist deliberately: this one was the first, FastAPI
version; the other was built specifically to learn Django's REST
framework, applied to the same problem. Neither is a stub or a
leftover -- they're two independently working, independently tested
implementations of the same domain logic.
